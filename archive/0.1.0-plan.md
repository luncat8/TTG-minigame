# 0.1.0 — Gravity-grid minigame

## Objective

Build a playable, file://-friendly browser game for several players on a square grid. Players place symbols while gravity changes direction; configurable match and removal rules determine scoring. The first playable configuration is a 7×7 board with three players.

## Runtime and implementation constraints

- Use HTML, CSS, and classic JavaScript; no build step, ES modules, remote assets, or runtime network requests.
- Keep the board and controls usable when the page is opened directly from disk.
- Use one tab for indentation and LF line endings. Keep frame/render paths allocation-light: all rule buffers are typed arrays allocated when a board size is created.
- Keep game rules deterministic and independently testable. Each script guards its export so rule and bot code runs under Node without a bundler.
- Tests and measurement scripts use only Node built-ins (`node:test`, `assert`, `fs`).

## Constants

| Item | Value |
| --- | --- |
| Active players | 2–6, default 3 |
| Player slots | 6 fixed slots; each has one symbol shape and one pastel color |
| Board size | 5–11, default 7 (square) |
| Window length | 3 |
| Default group-removal threshold | 4 (model option `groupMinSize`; not exposed in UI until tuning is decided) |
| Gravity cycle | down → left → up → right → down (clockwise on screen) |

## Gameplay baseline

### Board and turns

- Each occupied cell belongs to one player slot. Empty cells are the only legal placements.
- Gravity starts downward. The board stays upright; gravity changes instead. The edge toward which pieces fall is highlighted and marked with an arrow in the board margin.
- On a turn, the active player may rotate gravity one step clockwise, at most once per turn, or leave it unchanged. The player then places a symbol in an empty cell.
- Turns cycle through the active slots 0…(active count − 1) in ascending order.
- One turn resolves in this order:
  1. Place the symbol.
  2. Settle all pieces toward the current gravity edge, keeping the relative order of pieces within each row or column.
  3. Detect all matches on the settled board, for every player.
  4. Award points.
  5. Remove the union of cells selected by enabled removal rules.
  6. Settle again toward the current gravity edge. Matches that appear only because of this final settle are not detected in this resolution; they are detected at the next resolution.
  7. Refresh the match snapshot (see scoring policy).
  8. If the board has no empty cell, the game ends. Otherwise advance to the next active player.
- The game ends when the board is full after a resolution. The winner is the highest score among the active players at that moment; equal top scores are a tie.
- Clean starts a fresh board without changing the selected options.

### Match definitions

- A window is three consecutive cells in one direction (horizontal, vertical; diagonal when enabled) that all belong to the same player.
- Overlapping windows are distinct. Four in a row contains two windows.
- Diagonal windows run both down-right and down-left.
- A group is a set of same-player cells connected orthogonally (not diagonally). A diagonal-only contact does not connect a group.

### Rule controls and defaults

Provide a checkbox for each rule, initialized as follows:

| Rule | Default | Behavior |
| --- | --- | --- |
| Score three in a horizontal or vertical row | On | Award one point to the owner of each qualifying linear window. |
| Score diagonal threes | Off | Include both diagonal directions when enabled. |
| Remove scored three-cell matches | Off | Remove the union of cells of all qualifying windows of enabled directions, after scoring. |
| Remove any group of four or more | On | Remove an entire same-player orthogonal group with at least `groupMinSize` cells. |
| Score every turn after gravity resolves | On | Re-award all qualifying windows after each resolution. When off, award only windows that were not qualifying at the previous snapshot. |

Rule policy:

- Evaluate every player's windows and groups on the same settled board, so a gravity change can score or clear any player's symbols.
- Detection precedes removal; points are awarded before any cell is cleared.
- Removals are simultaneous (one union mask, applied once).
- No rule change awards points by itself. A rule change refreshes the snapshot from the current board under the new rules, and its effects appear from the next resolution.

#### Snapshot policy (score-only-new)

- The snapshot is the set of qualifying windows detected in step 3 of the latest resolution, identified by window position and owner.
- A window is new when its position and owner were absent from that snapshot.
- Windows formed only by the final settle (step 6) are absent from the snapshot, so the next resolution scores them as new. This is the deferral rule.
- Resize and rule changes refresh the snapshot without scoring.

### Settings and player controls

- Controls: active player count (2–6, default 3), board size (5–11, default 7), per-slot Human/Bot selection (default Human), and per-slot bot strategy selection from the bot registry.
- Settings take effect immediately and never invoke Clean.
- Board size:
  - Growing adds empty cells on the right and bottom.
  - Shrinking keeps the overlapping top-left area and removes pieces cropped outside the new bounds.
  - Then the board is settled toward the current gravity, with no scoring, and the snapshot is refreshed.
  - If the result is a full board, the game ends.
- Player count:
  - Changing the count updates the turn order without clearing the board.
  - A slot removed from the active range keeps its marks, score, and controller setting, and stays visible as inactive until Clean.
  - Marks of an inactive slot remain ordinary board pieces: they settle, block cells, score into their own row, and can be removed. The slot takes no turns.
  - Re-activating a slot restores its marks, score, and controller.
  - If the player on turn is deactivated, the turn passes to slot 0.
- Clean removes all marks, resets scores and gravity to down, clears the snapshot, and clears the game-over state. It keeps the board size, player count, controllers, bot selections, and rule settings.

## Bot

- Implement one selectable gravity-aware heuristic bot and register it in the bot registry. The registry populates the strategy dropdowns.
- The bot evaluates each candidate `(gravity choice, empty cell)` by simulating the normal turn resolution on a scratch copy of the board. It never mutates the live game.
- Candidate score, in points:
  - immediate points for the bot minus immediate points for all other active players in this resolution;
  - plus `STANDING_VALUE` (1.5) for each qualifying window the bot owns after the resolution, minus the same for each window owned by other players. This is a future-income proxy for threes that keep scoring each turn;
  - minus the best immediate gain the next active player can get from one of their own placements on the candidate board, which denies immediate opponent scoring.
- Preference order on ties: keep gravity over rotating; lower cell index first. Results are deterministic for the same position.
- A standing three is worth more than extending it into a group that will be removed: extending a three to four (when group removal is on and scoring is every turn) loses the standing three's future income, and the standing-value term captures this.
- Rotating gravity is a candidate only if the player has not rotated this turn.
- Scratch buffers are allocated once per board size and reused.

## Implementation sequence

1. **Fix rule semantics.** Rules live in the model, not in UI code.
2. **Build the pure game model** (`src/model.js`). Represent slots, board cells, gravity, scores, active slot, rule options, and snapshot. Implement placement, stable settling in four directions, window detection, group detection, scoring, simultaneous removal, turn advancement, resize, rule changes, Clean, and game-over.
3. **Test the rules** (`test/model.test.js`). Cover:
   - gravity in each direction, stable order;
   - horizontal, vertical, and diagonal windows;
   - overlapping windows;
   - four-connected versus diagonal-only groups;
   - each rule toggle;
   - repeated versus newly formed scoring, including deferred matches;
   - resize and player-count changes;
   - full-board termination;
   - one rotation per turn.
4. **Build the bot** (`src/bots.js`) and its tests (`test/bots.test.js`). Test that it returns only legal moves, does not mutate the live game, and prefers keeping a standing three over extending it into a removable group in a targeted position.
5. **Build the page and rendering** (`index.html`, `style.css`, `src/render.js`). Accessible DOM controls; a canvas board renderer with pastel cells, symbols, the active player, scores, the gravity arrow and highlighted target edge, hover preview, and a full-board/game-over state. Classic `<script>` tags in dependency order.
6. **Wire interaction** (`src/app.js`). Rotate gravity, place by click or keyboard (arrow keys move a cursor, Enter places, `R` rotates), turn progression, bot turns with short delays, immediate settings, and Clean. Settings changes cancel any scheduled bot move before re-scheduling.
7. **Self-play and tuning** (`experiments/selfplay.js`). Run bot-only games under the default rules, and compare group-removal thresholds 4 and 5 by group-clear frequency, points per turn, game length, and score spread. Keep logs in `experiments/logs/`. The default changes only after a human playtest supports it.

## Acceptance criteria

- Opening `index.html` directly from disk shows an interactive 7×7 board, three player rows, and the defaults above.
- Gravity can change without rotating the board, is visibly indicated, and settles pieces correctly in every direction.
- Human turns, the bot, scoring, removals, live settings, game-over feedback, and Clean work without a page reload.
- Rule changes are independent and match the stated defaults; a disabled removal rule never clears its patterns.
- Live configuration changes never require Clean and never award points by themselves.
- `node --test` passes with no third-party packages or build tooling.

## Open questions

- Group-removal threshold: the default is 4. Self-play comparison against 5 is in `experiments/`. Changing the default needs a playtest.
- Strategy options: a deeper search or a second strategy would be a new registry entry. It does not change the model.
